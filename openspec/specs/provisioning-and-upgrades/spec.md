# Подготовка устройств и обновления

## Purpose

Эта возможность формирует универсальный полный образ DietPi, создаёт уникальную идентичность каждой установки и безопасно обновляет работающие устройства.

## Requirements

### Requirement: Универсальный SD-образ

Система SHALL создавать один повторно используемый загрузочный ZIP-образ на базе DietPi RPi 2/3/4 ARMv8 с именем `exxpiano-rpi234-v<версия>-dietpi-<версия-dietpi>-sd.zip`. Образ SHALL предназначаться для непосредственной записи на чистую SD-карту и SHALL содержать приложение, банк фортепиано `full`, банк механики, README и машиночитаемый манифест. Сборка MUST NOT запрашивать serial платы или другой идентификатор устройства. Первый запуск MUST завершать локальную подготовку без интернета, Ethernet и сохранённой Wi-Fi.

#### Scenario: Один образ для нескольких устройств

- **WHEN** оператор записывает один поставляемый ZIP на несколько чистых SD-карт и впервые запускает их в совместимых Raspberry Pi
- **THEN** каждая карта загружается без предварительной установки ОС и без ввода serial платы

#### Scenario: Прослеживаемость выпуска

- **WHEN** сборка успешно завершена
- **THEN** имя ZIP содержит версии продукта и DietPi, а README и манифест содержат эти версии и SHA-256 исходного образа DietPi

#### Scenario: Обязательный банк отсутствует

- **WHEN** основной или явно выбранный банк фортепиано либо механики отсутствует или непригоден
- **THEN** система завершает сборку ошибкой и не выдаёт ZIP как готовый

#### Scenario: Секреты сборки

- **WHEN** образу передаются root-пароль и пароль setup-сети
- **THEN** сборщик передаёт их во внутреннюю среду, не включает в аргументы команд и не записывает в журнал

### Requirement: Идентичность установки

Каждая установленная копия SHALL при первом запуске автоматически создавать и постоянно хранить случайный 64-битный идентификатор в виде 16 шестнадцатеричных символов. Пользователь MUST NOT вводить serial платы или идентификатор установки. Полный идентификатор SHALL входить в setup SSID `exxpiano-Setup-<ID>` и hostname `exxpiano-<id-в-нижнем-регистре>`, а web API и QR-коды SHALL показывать тот же идентификатор. Создание SHALL быть атомарным, а последующие запуски SHALL повторно использовать сохранённое значение.

#### Scenario: Первый запуск клонированных карт

- **WHEN** две карты, записанные из одного ZIP, запускаются впервые
- **THEN** каждая независимо создаёт свой постоянный идентификатор и использует его в setup SSID и hostname

#### Scenario: Повторный запуск

- **WHEN** установка уже имеет сохранённый корректный ID
- **THEN** система сохраняет прежние setup SSID и hostname и не создаёт новый ID

#### Scenario: QR-код другого устройства

- **WHEN** web-интерфейс открыт по QR-коду с ID, отличным от ID текущей установки
- **THEN** web-интерфейс предупреждает, что код принадлежит другому устройству

### Requirement: Безопасное обновление работающего устройства

Система SHALL перед обновлением сохранять предыдущую установленную версию и конфигурацию, проверять возврат синтезатора и MIDI-моста и автоматически откатываться при неудаче.

#### Scenario: Успешное обновление

- **WHEN** новый пакет устанавливается и обе основные службы становятся рабочими
- **THEN** новая версия остаётся активной, а пользовательская конфигурация, идентификатор установки и звуковые банки сохраняются

#### Scenario: Служба не восстановилась

- **WHEN** после обновления синтезатор или MIDI-мост не становится рабочим за отведённое время
- **THEN** система восстанавливает предыдущий пакет и конфигурацию и сообщает о выполненном откате

### Requirement: Проверка и публикация сборок

CI SHALL запускать быстрые автоматические тесты для push и pull request. Публичные CI-артефакты и релизы MUST NOT содержать отдельные Debian-пакеты или ZIP/TAR.GZ-инсталлятор для установки поверх DietPi. Полный DietPi-образ SHALL формироваться отдельно при изменениях конвейера или выпуске. Релизная сборка SHALL получать закреплённую неизменяемую копию официальной основы DietPi из отдельного GitHub prerelease и MUST проверить записанный в репозитории SHA-256 до изменения образа. Тег `v<VERSION>` SHALL запускать формирование GitHub Release, а релизный тег MUST совпадать с файлом `VERSION`. GitHub Release SHALL иметь английский заголовок с названием продукта, версией и семейством Raspberry Pi и английское описание состава, установки, первого запуска и проверки контрольных сумм. Он SHALL содержать универсальный ZIP-образ, README, машиночитаемый манифест и файл SHA-256 контрольных сумм и MUST NOT публиковаться при ошибке сборки или проверки образа.

#### Scenario: Проверка обычного изменения

- **WHEN** изменение не затрагивает формирование полного образа
- **THEN** CI запускает быстрые тесты и не запускает полный образный конвейер

#### Scenario: Выпуск образа

- **WHEN** оператор публикует тег, соответствующий `v<VERSION>`
- **THEN** CI создаёт GitHub Release с заголовком и описанием и прикладывает универсальный ZIP с DietPi, приложением и обязательными банками, README, манифест и файл контрольных сумм

#### Scenario: Проверка закреплённой основы DietPi

- **WHEN** CI начинает релизную сборку по тегу версии
- **THEN** он скачивает основу DietPi из отдельного GitHub prerelease и продолжает только при совпадении SHA-256 с закреплённым значением

#### Scenario: Ошибка формирования образа

- **WHEN** сборка банков, образа или его автоматическая проверка завершается ошибкой
- **THEN** GitHub Release с этим образом не публикуется

#### Scenario: Несовпадающий релизный тег

- **WHEN** tag build использует версию, отличную от `VERSION`
- **THEN** публикация релиза завершается ошибкой до прикрепления артефактов

### Requirement: Консоль без запроса пароля

Образ SHALL показывать на локальной консоли информационный экран с ID установки, именем и адресами web-интерфейса управления вместо приглашения входа. Консоль MUST NOT запрашивать логин или пароль, MUST NOT показывать секреты и MUST NOT включать автовход. Администрирование SHALL оставаться доступным по SSH.

#### Scenario: Первый запуск с подключённым HDMI

- **WHEN** карта запускается впервые с подключённым монитором
- **THEN** вместо приглашения `login:` на экране информационный экран, который обновляется и не принимает ввод

#### Scenario: Устройство без сети

- **WHEN** у устройства нет адреса
- **THEN** экран называет setup-сеть этой установки и адрес web-интерфейса setup

#### Scenario: Сборка образа

- **WHEN** выполняется сборка или смоук-проверка образа
- **THEN** они проверяют наличие экрана и drop-in и отсутствие файла автовхода

### Requirement: Образ не создаёт QR-кодов

Сборка SD-образа SHALL NOT создавать QR-коды, наклейки или файлы с ними, потому что идентификатор установки неизвестен до первого включения. Единственным источником QR-кодов SHALL быть web-интерфейс установленного устройства.

#### Scenario: Сборка образа

- **WHEN** выполняется сборка SD-образа
- **THEN** в результате нет QR-кодов, изображений наклеек и скриптов их автономного создания
- **AND** смоук-проверка образа убеждается, что web-интерфейс устройства строит код из сгенерированного installation ID, а не из фиксированного имени

### Requirement: Банк по объёму памяти платы

Образ SHALL содержать уменьшенный банк `piano-lite.sf2`, а первый запуск на плате с памятью меньше 800 МБ MUST выбрать его вместо `piano.sf2`.

#### Scenario: Плата с 512 МБ

- **WHEN** образ запускается впервые на плате, у которой `MemTotal` меньше 800 МБ
- **THEN** в `/etc/exxpiano.conf` значение `PIANO_SF2` указывает на `piano-lite.sf2`

#### Scenario: Плата с 1 ГБ

- **WHEN** образ запускается впервые на плате с 1 ГБ
- **THEN** `PIANO_SF2` остаётся `piano.sf2`
