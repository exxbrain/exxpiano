# Design

## Context

Мотивация и пользовательский scope описаны в `proposal.md`. Сейчас `banklib.py` безопасно читает плоский каталог банков, `sf2info.py` ограниченно разбирает RIFF/SoundFont, а `exxpiano-web.py` переключает банк с проверкой готовности FluidSynth и откатом. Отдельного владельца USB block devices, постоянной управляемой библиотеки импортов и прогресса длительной операции нет. Импорт выполняется только после запуска уже установленного устройства и не является этапом формирования первоначального SD-образа.

Raspberry Pi 3 делит USB 2.0 между накопителем, аудиоинтерфейсом, MIDI и Ethernet, имеет около 1 ГБ RAM и чувствительна к питанию. Поэтому hardware spike является входным условием для окончательной настройки копирования и списка файловых систем, но чистая логика и API остаются детерминированно тестируемыми на Mac/Linux.

## Goals / Non-Goals

**Goals:**

- Один владелец жизненного цикла USB-накопителя и один сериализованный импорт.
- Недоверенные имена и содержимое никогда не превращаются в произвольные filesystem paths или команды.
- Частичный файл никогда не появляется в основном каталоге банков.
- Существующие установленные банки и API переключения продолжают работать.
- После импорта USB-накопитель больше не нужен.
- Состав и состояние библиотеки импортов не влияют на имя, манифест, версию или готовность первоначального образа устройства.

**Non-Goals:**

- SFZ, импорт или замена `mech.sf2`, автоматический импорт и аппаратная кнопка.
- Запуск FluidSynth непосредственно с USB-накопителя.
- NTFS до подтверждения потребности и доступного драйвера на целевом DietPi.
- Полный перевод существующих root-служб на непривилегированных пользователей в рамках этого change.
- Добавление пользовательских банков в первоначальный образ или изменение его производственного конвейера.

## Decisions

### 1. Разделить монтирование и пользовательские операции

Привилегированный helper, запускаемый udev/systemd, монтирует поддерживаемый раздел read-only с `nosuid,nodev,noexec` под контролируемым путём и атомарно публикует status JSON в `/run`. Веб-служба не принимает device path и работает только с опубликованным идентификатором накопителя и идентификаторами найденных файлов.

Альтернатива — монтировать прямо из HTTP handler — смешивает недоверенный запрос, root subprocess и длительный I/O и усложняет восстановление после извлечения.

### 2. Управляемая библиотека с непрозрачными идентификаторами

Каждый импорт хранится как `/var/lib/exxpiano/banks/<id>/bank.sf2` или `bank.sf3` рядом с `meta.json`. Идентификатор выводится из SHA-256 и не зависит от исходного имени. Метаданные содержат отображаемое имя, размер, checksum, сведения SoundFont и необязательные author/licence из строго ограниченного `bank.json`.

Каталог банков объединяет существующий `BANK_DIR` и managed imports. Для совместимости существующие filename-id остаются прежними; импортированные элементы получают отдельный namespace идентификаторов. В конфигурацию по-прежнему записывается проверенный абсолютный `PIANO_SF2`.

Альтернатива — складывать импортированные файлы рядом с пакетными в `/opt` — смешивает изменяемые данные с приложением и делает поведение upgrades неявным.

### 3. Транзакция импорта

Importer повторно разрешает выбранный source ID по актуальному status, открывает обычный файл без следования ссылкам, заранее проверяет лимиты памяти и диска, копирует в уникальный временный каталог на том же filesystem, одновременно считает SHA-256, затем повторно проверяет SoundFont и размер. Только после `fsync` данных и каталога временный каталог атомарно переименовывается в `<id>`.

Ошибка, hot-unplug, disk full или отмена удаляют временный каталог. Совпадение checksum возвращает существующий импорт. Один lock сериализует import/delete и предотвращает гонки с выбором банка.

### 4. Status-файл вместо длительного HTTP-запроса

Запуск импорта быстро возвращает accepted + operation ID. Worker публикует атомарный status JSON с фазой, счётчиками и безопасной ошибкой. Существующий `/api/state` или отдельный `/api/usb-banks` возвращает снимок; браузер опрашивает его. Это сохраняет простой standard-library HTTP server и переживает разрыв клиентского соединения.

### 5. Удаление под ограничениями bank-management

Delete принимает только imported ID, повторно разрешает его через managed index и отказывает для текущего `PIANO_SF2` и `PIANO_SF2_LAST_GOOD`. Сначала запись исчезает из опубликованного каталога, затем её каталог удаляется; установленным банкам этот API недоступен.

### 6. Runtime-поддержка файловых систем

Первая версия явно поддерживает FAT32 и exFAT; ext4 работает при наличии штатной поддержки ядра. NTFS не добавляется. Hardware spike проверяет фактический DietPi, `systemd-mount`, udev remove events и поведение при неожиданном извлечении до фиксации состава зависимостей. Helper, systemd units, udev rules и подтверждённые зависимости входят в обычную установку runtime-приложения; решение не привязывается к публичному `.deb`, отдельному DietPi installer или сборке первоначального SD-образа.

## Risks / Trade-offs

- [USB-копирование вызывает аудио dropouts] → измерить 400 МБ copy на реальной Pi с MIDI и USB audio; при необходимости ограничить скорость и показывать предупреждение не играть во время импорта.
- [Вредоносный SoundFont атакует FluidSynth] → bounded parser, лимиты размера, read-only/noexec mount и отдельная будущая работа по запуску FluidSynth без root; полную безопасность C-парсера гарантировать нельзя.
- [Извлечение или disk full оставляет мусор] → same-filesystem temp directory, атомарный rename, startup cleanup только для подтверждённых stale temp directories.
- [Слабое питание с тремя USB-устройствами] → проверять throttling в hardware checklist и рекомендовать powered hub при зафиксированном undervoltage.
- [Существующий `BANK_DIR` указывает на `/opt`] → агрегатор сохраняет его как installed source, managed imports живут отдельно в `/var/lib`; миграция существующих файлов не требуется.
- [Служба web пока root] → минимизировать поверхность через ID-based API и фиксированный helper; полноценное privilege separation оформить отдельным change.

## Migration Plan

1. Установить managed library, helper, unit/rule-файлы и новые API вместе с runtime-приложением без изменения текущего `PIANO_SF2` и без пересборки первоначального образа как части операции импорта.
2. При первом запуске создать `/var/lib/exxpiano/banks` и удалить только stale temp entries известного формата.
3. Оставить существующие банки и профили без миграции; новые импорты добавляются вторым источником.
4. При rollback удалить новые unit/rule-файлы и остановить helper, сохранив импортированные данные в `/var/lib`; старая версия продолжит играть текущий installed bank либо явно выбранный абсолютный путь, если он ещё существует.
5. Выполнить hardware checklist на Raspberry Pi 3 до объявления функции проверенной на оборудовании.
