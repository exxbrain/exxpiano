# Сборка универсального образа SD-карты

Поставляемый артефакт — один полный загрузочный образ для чистой SD-карты, который запускает **Raspberry Pi 3, 4 или 5** (64 бита). В нём Alpine Linux 3.24 (sys-режим на ext4, OpenRC), пакеты exxpiano, полное фортепиано и банк механики, а также уменьшенное фортепиано `lite` для плат с 512 МБ. Один ZIP можно записывать на несколько карт. Raspberry Pi 2 не поддерживается.

Образ не собирается из готового образа дистрибутива: сборщик ставит пакеты Alpine в пустую корневую файловую систему из ветки и HTTPS-зеркала, закреплённых в `alpine/repositories`, а `apk` проверяет подпись каждого индекса и пакета официальными ключами из `alpine/keys/` (их SHA-256 записаны в `.github/alpine-image.env`). Несовпадение останавливает сборку. Стабильная ветка Alpine заменяет пакеты исправленными сборками и не хранит старые версии, поэтому две сборки в разные дни могут отличаться; манифест каждого образа перечисляет все пакеты с точными версиями.

## Подготовка

Нужны Docker Desktop на macOS (на Apple silicon он запускает arm64-сборщик без эмуляции) или Docker на Linux-машине arm64. Подготовьте банки:

```bash
scripts/make-soundfonts.sh -p full -o build
scripts/make-soundfonts.sh -p lite -o build
```

По умолчанию сборщик использует `build/piano-full.sf2`, `build/piano-lite.sf2` (если он есть) и `build/mech.sf2`. Другие банки передаются через `--piano`, `--piano-lite` и `--mech`. Образ без фортепиано и механики не собирается; первый запуск на плате с памятью меньше 800 МБ (Pi 3 A+) выбирает банк `lite`.

Соберите пакеты (они подписаны, см. ниже):

```bash
python3 scripts/build-apks.py
```

Получится `dist/apk/exxpiano/aarch64/` (`exxpiano`, а также `py3-mido` и `py3-python-rtmidi`, которых нет в Alpine: они собираются без изменений из закреплённых выпусков на PyPI) со своим `APKINDEX.tar.gz` и `dist/apk/<ключ>.rsa.pub` — публичный ключ, которому будет доверять образ.

**Ключ подписи.** `EXXPIANO_APK_KEY` содержит приватный ключ (PEM), `EXXPIANO_APK_KEY_NAME` — его имя (`exxpiano`). Без них пакеты подписываются ключом разработки, который один раз создаётся в `build/apk-key/`, и сборщик об этом предупреждает: такой образ — только для своих устройств. Релизный workflow берёт ключ из секрета `EXXPIANO_APK_KEY` и без него останавливается. Ключ проекта создаётся один раз:

```bash
openssl genrsa -out exxpiano.rsa 4096        # хранить вне репозитория; содержимое положить в секрет EXXPIANO_APK_KEY
```

## Сборка

Пароли лучше передавать через окружение, чтобы они не попадали в список процессов:

```bash
printf 'Пароль root (SSH; пусто — вход только по ключу): '; read -r -s SD_PASSWORD; printf '\n'
printf 'Пароль сети настройки: '; read -r -s SD_AP_PASSWORD; printf '\n'
export SD_PASSWORD SD_AP_PASSWORD

python3 scripts/build-sd-image.py --country RU --timezone Europe/Moscow --dry-run
python3 scripts/build-sd-image.py --country RU --timezone Europe/Moscow

unset SD_PASSWORD SD_AP_PASSWORD
```

`--dry-run` проверяет входные данные и выводит план. `--ssh-key ~/.ssh/id_ed25519.pub` кладёт в образ публичный ключ для root. Полный запуск пишет в `dist/sd/`:

- `exxpiano-rpi-v<VERSION>-alpine-<ВЕРСИЯ_ALPINE>-sd.zip` — образ для записи;
- `manifest.json` — версии продукта и Alpine, закреплённые ветка, зеркало и суммы ключей, ключ подписи пакетов, все установленные пакеты с версиями, банки, контрольные суммы образа и схема идентичности;
- `README.txt` — краткая инструкция для этого выпуска.

Как делается образ (`scripts/sd-image-inner.sh` в контейнере `sd-builder`): `apk --root --initdb` ставит `alpine-base`, ядро `linux-rpi`, прошивку `raspberrypi-bootloader` и прошивки Wi-Fi, eudev, OpenSSH, chrony, ifupdown-ng и `exxpiano`; службы попадают в runlevel-ы OpenRC (eudev вместо mdev, `hostapd` и `dnsmasq` выключены: их запускает `exxpiano-wifi`); на консоли `tty1` вместо getty информационный экран; `/etc/network/interfaces` настраивает только `eth0` (Wi-Fi принадлежит `exxpiano-wifi`). Затем программы образа запускаются в chroot: импортируются модули Python и MIDI-библиотеки, web-служба отвечает и строит QR-код setup-сети, экран консоли выводится. Корневая файловая система становится ext4-файлом через `mkfs.ext4 -d`, загрузочный раздел — FAT32-файлом через `mtools`; loop-устройства и привилегированный контейнер не нужны. Перед записью ZIP образ читается обратно (`debugfs`, `mdir`) и проверяется всё обещанное: ядро, initramfs и device tree для Pi 3, 4 и 5, `arm_64bit=1` и `dtparam=audio=on`, службы всех runlevel-ов, отсутствие getty и автовхода, банки, демонстрационные пьесы, отсутствие installation ID, страна Wi-Fi, доверенный ключ и отсутствие следов Debian и DietPi.

> **Вход root.** С `SD_PASSWORD` root входит по SSH с этим паролем. Без него у root нет пароля и вход возможен только по ключу: передайте `--ssh-key` или положите свой публичный ключ в файл `authorized_keys` на загрузочный раздел карты (FAT-раздел, который открывается на любом компьютере). При каждом запуске устройство добавляет ключи из этого файла для root.

> **Пароль setup-сети.** Без `SD_AP_PASSWORD` в образе остаётся пароль по умолчанию `exxpianosetup`, одинаковый для всех карт из этого образа; имя сети у каждой карты своё (оно заканчивается installation ID). С `SD_AP_PASSWORD` все карты этого образа получают ваш пароль. На отдельном устройстве он меняется параметром `WIFI_AP_PASSWORD` в `/etc/exxpiano.conf`.

## GitHub Release

Перед тегом релиза добавьте в `CHANGELOG.md` раздел `## <VERSION>`: workflow добавляет его в описание GitHub Release (`scripts/release-notes.py`) и без него останавливается.

Тег `v<VERSION>` запускает `.github/workflows/release.yml` на arm64-раннере. Workflow проверяет, что тег совпадает с `VERSION` и секрет `EXXPIANO_APK_KEY` задан, запускает быстрые тесты, собирает банки full и lite, подписанные пакеты, собирает и проверяет образ и создаёт GitHub Release с файлами:

- `exxpiano-rpi-v<VERSION>-alpine-<ВЕРСИЯ_ALPINE>-sd.zip`;
- `manifest.json`;
- `README.txt`;
- `SHA256SUMS`.

Отдельных `.apk` в релизе нет: устройство обновляется через `scripts/deploy-to-pi.sh`. В названии — exxpiano, версия и платы. Если любой предыдущий шаг завершился ошибкой, релиз не создаётся. У существующего релиза обновляются название и описание и добавляются недостающие файлы; файл с уже существующим именем никогда не перезаписывается (загрузка завершится ошибкой, решение за оператором).

Обычные push и pull request запускают только быстрые тесты. `.github/workflows/image-pipeline.yml` запускается при изменении упаковки, служб или сборщика образа (или вручную): собирает пакеты, запускает службы OpenRC в контейнере (`scripts/test-openrc-services.sh`), устанавливает, обновляет, откатывает и удаляет пакеты (`scripts/test-apk-upgrade.sh`) и собирает полный образ с банками-заглушками (`scripts/test-sd-image-pipeline.sh`).

### Зеркало для скачивания

Образы весят около 1 ГБ, и с GitHub они могут качаться медленно. Поэтому workflow выпуска также копирует файлы релиза в публичный бакет Cloudflare R2 (`scripts/mirror-to-r2.sh`, в `<bucket>/<tag>/`) и добавляет в описание релиза раздел **Faster download (mirror)** со ссылками на ZIP-файлы. R2 не берёт плату за скачивание, а 10 ГБ хранения бесплатны. Настройка делается один раз:

1. В Cloudflare создайте бакет R2 и сделайте его публичным: подключите к нему свой домен (рекомендуется) или включите адрес `r2.dev` (Cloudflare ограничивает его скорость).
2. Создайте API-токен R2 с правом **Object Read & Write** на этот бакет.
3. В настройках репозитория добавьте секреты `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET` и переменную (не секрет) `R2_PUBLIC_URL`: публичный адрес бакета без слэша в конце: свой домен или `https://pub-….r2.dev` из **Settings → Public access** бакета, а не адрес S3 API `https://<account>.r2.cloudflarestorage.com` (он требует авторизации; с ним копирование остановится с ошибкой).

На зеркале хранятся только две последние версии: после каждого выпуска (и каждого запуска **release-mirror**) более старые папки `v*` удаляются из бакета, а ссылки на зеркало убираются из описаний этих релизов; сами файлы остаются в GitHub Releases. Без `R2_PUBLIC_URL` эти шаги пропускаются. Ошибка копирования не останавливает выпуск: релиз публикуется без ссылок на зеркало, а копирование можно повторить. Для релиза, выпущенного до появления зеркала или с неудачным копированием, запустите на вкладке **Actions** workflow **release-mirror** с его тегом: он скачает файлы релиза, проверит их по `SHA256SUMS`, скопирует в бакет и добавит ссылки на зеркало в опубликованное описание, не меняя остальной текст.

## Запись и первый запуск

1. В Raspberry Pi Imager выберите «Choose OS» → «Use custom» и укажите ZIP либо выберите ZIP в balenaEtcher.
2. Запишите чистую SD-карту, вставьте её в Raspberry Pi 3, 4 или 5 и включите питание.
3. Первый запуск занимает минуту-две и не требует интернета, Ethernet или сохранённой Wi-Fi: корневой раздел расширяется на всю карту (`growpart`, `resize2fs`), создаётся имя устройства, плата с малой памятью получает банк `lite`.
4. Установка сама создаёт постоянный случайный ID из 6 шестнадцатеричных символов в `/var/lib/exxpiano/installation-id`.
5. Из ID получаются уникальные сеть `exxpiano-Setup-<ID>` и hostname `exxpiano-<id-в-нижнем-регистре>`. Подключитесь к setup-сети и откройте `http://10.42.0.1:8080/`; точные ID, имя сети и QR-коды показаны в web-интерфейсе.

Клонированные из одного ZIP карты получают разные ID при своём первом запуске. ID создаётся атомарно и затем не меняется, поэтому перезапуск не меняет Wi-Fi или hostname.

## Переход устройства с DietPi

Карту из образа DietPi (версия 1.10.22 и старше) нельзя обновить до Alpine на месте: запишите новый образ. Чтобы сохранить накопленное устройством, сначала скопируйте его (устройство доступно как раньше):

```bash
scp -r root@<устройство>:/var/lib/exxpiano ./exxpiano-data          # installation ID, импортированные банки, профили, MIDI-библиотека
scp root@<устройство>:/etc/exxpiano.conf ./exxpiano-data/
scp root@<устройство>:/etc/wpa_supplicant/wpa_supplicant.conf ./exxpiano-data/     # сохранённые сети Wi-Fi
```

После первого запуска новой карты верните их от имени root и перезапустите устройство:

```bash
scp -r ./exxpiano-data/* root@<устройство>:/tmp/restore/
ssh root@<устройство> 'cp -a /tmp/restore/. /var/lib/exxpiano/ && mv /var/lib/exxpiano/exxpiano.conf /etc/ && mv /var/lib/exxpiano/wpa_supplicant.conf /etc/wpa_supplicant/ && reboot'
```

После перезагрузки устройство снова называется по старому installation ID (setup-сеть и hostname следуют за ним).

## Проверка

Для обычных изменений запускайте быстрые тесты:

```bash
python3 -m unittest discover -s tests
```

Контейнерные проверки и сборку образа запускайте при изменениях упаковки или сборщика либо перед выпуском (GitHub Actions соблюдает то же разделение):

```bash
scripts/test-openrc-services.sh
scripts/test-apk-upgrade.sh
scripts/test-sd-image-pipeline.sh
```

Контейнер — не Raspberry Pi. **Образ на Alpine запускался только на Raspberry Pi 3 Model B** (проверки устройства по SSH делает `deploy/check-on-pi.sh`: `ssh root@<устройство> sh -s < deploy/check-on-pi.sh`). На Pi 3, 4 и 5 проверьте `/var/log/exxpiano-firstboot.log`, расширенный корневой раздел, экран консоли, уникальную setup-сеть и подключение к Wi-Fi, web-интерфейс, звук через разъём 3,5 мм и USB-карту, подключение и отключение USB-звуковой карты, накопителя и MIDI-клавиатуры, задержку FluidSynth по сравнению с DietPi, обновление и откат через `scripts/deploy-to-pi.sh` и повторный автономный запуск.
