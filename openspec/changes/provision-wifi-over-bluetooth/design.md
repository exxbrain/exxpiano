# Design

## Context

См. `proposal.md` — Why. Сейчас `exxpiano-wifi` является единственным владельцем `wlan0`: web-служба валидирует ввод, преобразует пароль в PSK и обменивается с supervisor приватными одноразовыми request/status-файлами в `/run/exxpiano-wifi`. В образ не входят BlueZ или BLE-служба, а клиентом настройки является web-интерфейс внутри setup-сети.

Pi 3/4 имеют встроенный BLE, тогда как Pi 2 требует USB-адаптер. Устройство не имеет обязательного экрана для показа случайного pairing-кода. Формат универсального образа и генерация installation ID при первом запуске должны сохраниться.

## Goals / Non-Goals

**Goals:**

- добавить BLE как второй transport к существующей транзакционной настройке Wi-Fi;
- сохранить одного владельца сетевой конфигурации и одинаковый откат для web и BLE;
- дать одинаковый пользовательский поток Android/iOS;
- ограничить время атаки и жизненный цикл открытого секрета;
- деградировать к существующей setup-сети без влияния на запуск пианино.

**Non-Goals:**

- управление звуком, банками или обновлениями через BLE;
- замена web-интерфейса либо удаление setup Wi-Fi;
- поддержка Web Bluetooth как обязательного клиента;
- обещание BLE на Pi 2 без USB-адаптера;
- изменение формата `wpa_supplicant` или хранение открытого пароля.

## Decisions

### 1. BLE-служба является адаптером, а не вторым Wi-Fi manager

Новая root-служба `exxpiano-bluetooth` публикует GATT API, валидирует протокол и использует функции `wifilib` для SSID, пароля и вывода PSK. Затем она пишет тот же одноразовый запрос, который обслуживает `exxpiano-wifi`, и наблюдает общий status-файл по request ID.

Альтернатива — изменять `wpa_supplicant` прямо из BLE-службы — отклонена: два владельца нарушили бы существующие гарантии atomic write, busy и rollback. Для web-службы и BLE-службы будет выделен общий transport-neutral helper формирования запросов, но сам supervisor останется единственным процессом, меняющим сеть.

### 2. BlueZ GATT через системный D-Bus

DietPi-образ получает `bluez`, `python3-dbus` и `python3-gi`. Python-служба регистрирует локальное GATT-приложение и advertisement в BlueZ через D-Bus. Это сохраняет runtime в существующем Python/Bash стеке и использует дистрибутивные пакеты; отдельный BLE-фреймворк из PyPI не нужен.

GATT-сервис имеет версионированный UUID и характеристики:

- `info` — protocol version, product version, installation ID и возможности;
- `control` — фрагментированные команды `scan`, `connect` и `cancel`;
- `status` — read/notify с busy, результатом, hostname/IP и кодом ошибки;
- `networks` — read/notify с фрагментированным результатом сканирования.

Сообщения — ограниченный UTF-8 JSON с номером версии, session nonce, request ID и лимитами размера. Фрагментация задаётся протоколом, чтобы не зависеть от согласованного BLE MTU. Неизвестная версия или команда отклоняется без побочного эффекта.

### 3. Окно настройки основано на состоянии устройства

Если сохранённых сетей нет, BLE advertisement автоматически открыт первые 15 минут после загрузки; незавершённая сессия может закончить текущий запрос, но не продлевает окно бесконечно. После успешного подключения advertisement и GATT-записи выключаются. На настроенном устройстве окно можно открыть на пять минут из web-интерфейса; локальный trigger оставляется конфигурируемой интеграционной точкой для аппаратной кнопки или MIDI-жеста, но не является условием первой версии.

Если начальное окно истекло, Bluetooth отсутствует или телефон несовместим, `exxpiano-wifi` продолжает обычный переход к setup-сети. Удаление последней сети снова делает установку ненастроенной и разрешает BLE-окно при следующем запуске.

### 4. Шифрование BLE обязательно, риск headless pairing явный

Характеристика `control` требует зашифрованного BLE-соединения и одной активной сессии. Session nonce и request ID не позволяют повторно применить команду из прошлой сессии. Пароль существует только в буфере активной сессии до вывода PSK и никогда не входит в GATT status, D-Bus logs или request-файл.

Без экрана или уникального напечатанного секрета режим Just Works не даёт защиты от активного MITM. Первая версия принимает этот риск в коротком окне первоначальной настройки, показывает полный installation ID в приложении и немедленно закрывает provisioning после успеха. Добавление proof-of-possession потребует отдельного решения о производственной маркировке или физическом trigger.

### 5. Мобильный клиент — React Native с TypeScript

Клиент располагается отдельно от web UI и использует нативный BLE-модуль React Native, поэтому поддержка не зависит от Web Bluetooth в браузере. Общий TypeScript-код реализует протокол и экраны, а платформенные части ограничиваются разрешениями Bluetooth, сканированием и переходом к системным настройкам при необходимости.

Приложение не требует учётной записи или облачного сервиса. Оно фильтрует устройства по service UUID, показывает полный installation ID, очищает пароль после отправки и предлагает открыть `http://<hostname>.local:8080/` после успеха.

### 6. Отсутствие Bluetooth — штатная деградация

BLE-служба ждёт BlueZ и адаптер, но завершается или остаётся неактивной без рестарт-цикла, если `hci0` отсутствует. Она не входит в зависимости запуска audio/MIDI/web/Wi-Fi служб. Pi 2 получает BLE только с протестированным USB-адаптером; конкретные chipset/VID:PID фиксируются после аппаратной проверки.

## Risks / Trade-offs

- [Just Works уязвим для активного MITM рядом с новым устройством] → короткое одноразовое окно, полный ID, одна сессия и явное последующее решение о proof-of-possession.
- [BlueZ или D-Bus недоступен] → не блокировать остальные службы и сохранить setup Wi-Fi.
- [Сканирование Wi-Fi конфликтует с текущим AP или подключением] → BLE запрашивает сканирование через существующий supervisor и получает cached/busy так же, как web.
- [BLE MTU различается между телефонами] → версионированное фреймирование с жёсткими лимитами и тестами границ.
- [React Native BLE ведёт себя по-разному на Android/iOS] → общий набор protocol fixtures плюс проверки на обоих реальных телефонах.
- [USB Bluetooth на Pi 2 несовместим с BlueZ или питанием] → публиковать только аппаратно проверенный список адаптеров и всегда сохранять fallback.

## Migration Plan

1. Добавить transport-neutral request/status helper и сохранить текущие web-тесты без изменения поведения.
2. Включить BlueZ-зависимости, BLE GATT-службу и systemd unit с безопасной деградацией без адаптера.
3. Добавить TypeScript-протокол и React Native приложение Android/iOS.
4. Обновить полный образ и двуязычную документацию, сохранив setup Wi-Fi как fallback.
5. Проверить stand-in без Bluetooth, затем реальный BLE provisioning на Pi 3/4 и Pi 2 с выбранным USB-адаптером и на Android/iOS.

Откат удаляет BLE-службу и мобильный клиент из поставки, но не требует преобразования сохранённых Wi-Fi-сетей: `exxpiano-wifi` и setup-сеть продолжают работать в прежнем формате.
