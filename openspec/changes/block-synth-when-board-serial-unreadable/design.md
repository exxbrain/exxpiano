# Design

## Context

См. `proposal.md` — Why. `exxpiano-run` вызывает `deviceid.py check` до выбора аудиоустройства и запуска FluidSynth. `deviceid.status()` уже различает совпадение (`True`), несовпадение (`False`) и невозможность сравнения (`None`), но `deviceid.check()` сейчас трактует `None` как разрешение. Shell-wrapper дополнительно пропускает проверку, если команда `python3` не найдена. Unit systemd уже содержит `RestartPreventExitStatus=78`.

## Goals / Non-Goals

**Goals:**

- Сделать блокировку fail-closed только при одновременно включённом `DEVICE_LOCK` и корректном `DEVICE_SERIAL`.
- Гарантировать, что FluidSynth не запускается без подтверждённого совпадения платы.
- Использовать единый постоянный exit 78 для несовпадения, unreadable serial и недоступного checker.
- Сохранить tri-state status для веб-интерфейса и диагностики.

**Non-Goals:**

- Менять правила нормализации или сравнения последних 32 бит serial.
- Блокировать карты без `DEVICE_LOCK=1` или без корректной привязки.
- Изменять формат `/etc/exxpiano.conf`, build-image CLI или веб-API.
- Превращать механизм учёта в криптографическую защиту от пользователя с root-доступом.

## Decisions

### 1. `deviceid.check()` является единственным решением о допуске

После проверки `locked` и `bound` функция возвращает 0 только для `status.ok is True`. И `False`, и `None` возвращают `EX_CONFIG` (78) с разными диагностическими сообщениями. `status()` остаётся tri-state: веб-интерфейс должен отличать несовпадение от отсутствия данных, даже если оба состояния блокируют синтезатор.

Альтернатива — преобразовать `None` в `False` внутри `status()` — стирает полезную причину отказа и ухудшает диагностику.

### 2. Shell-wrapper не пропускает обязательную проверку

При `DEVICE_LOCK=1` wrapper сначала убеждается, что `python3` доступен, затем запускает checker. Любая невозможность выполнить проверку завершает wrapper кодом 78 до операций с банками и ALSA. При выключенной блокировке checker по-прежнему не нужен.

Альтернатива — полагаться на пакетную зависимость Python — оставляет fail-open путь при повреждённой установке, хотя конфигурация явно требует блокировки.

### 3. Проверка остаётся детерминированной

Unit-тест передаёт `actual=None` напрямую. Shell-тест задаёт `EXXPIANO_CPUINFO` файлом без Serial и изолирует fallback device-tree так, чтобы checker гарантированно видел unreadable serial. Отдельный сценарий подставляет недоступный `python3` через контролируемый PATH или helper override. Оба теста проверяют exit 78 и отсутствие сформированной команды FluidSynth.

## Risks / Trade-offs

- [Временная ошибка чтения serial блокирует исправную плату] → это требуемое fail-closed поведение; stderr явно объясняет причину, а systemd не создаёт restart loop.
- [Неполная тестовая изоляция случайно читает serial хоста] → добавить тестовый override пути device-tree либо передавать `actual=None` на уровне unit-теста и полностью контролируемые пути на уровне shell-теста.
- [Обновлённый комментарий расходится между языками] → менять английскую и русскую документацию в одной задаче и проверять поиском старой fail-open формулировки.

## Migration Plan

Изменение не требует миграции конфигурации. После установки заблокированная карта продолжит запускаться только на плате с читаемым совпадающим serial. Rollback пакета восстанавливает старое fail-open поведение; данные пользователя не меняются.
